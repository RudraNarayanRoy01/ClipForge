# Identity Card Standard

## 1 Purpose

The Identity Card Standard answers ONE question and ONLY one question:

"How is every repository component uniquely and consistently identified?"

Identity Cards define identity. They DO NOT evaluate. They DO NOT inspect. They DO NOT review. They DO NOT certify. They DO NOT perform architecture analysis. They simply establish canonical identities. This document becomes the authoritative identity specification used by every downstream engineering artifact.

Identity Cards answer "What exactly is this component?", NOT "Is it correct?", NOT "Should it exist?", NOT "How good is it?", NOT "What changed?".

## 2 What This Standard Is NOT

This standard aggressively excludes:
- Repository Snapshot
- Repository Inspection
- Repository Review
- Architecture Verification
- Certification
- Architecture State
- Architecture Map
- Component Catalog
- Technical Debt
- Runtime Health
- Planning
- Roadmapping
- Implementation
- Prompt Generation
- AI Reasoning
- Repository Management
- Git
- Merge
- CI/CD
- Code Review
- Architecture Evaluation
- Quality Assessment
- Security Review
- Performance Review

## 3 Engineering Principles

The following engineering principles apply identically from Sprint 6A:
- **Repository Truth**: Only verifiable facts from the repository are permitted.
- **Evidence First Engineering**: Every finding must be backed by traceable evidence.
- **Deterministic Engineering**: The snapshot process must be repeatable and objective.
- **Scope Discipline**: The snapshot must not exceed its bounded scope.
- **Documentation Synchronization**: The snapshot must accurately reflect the documented state of the repository.
- **Repository Evidence**: Only use verifiable evidence.
- **Traceability**: Every fact must trace back to its origin.

## 4 Identity Authority

Authority derives ONLY from:
- Engineering Constitution
- Engineering Manual
- Approved Engineering Standards
- Repository Evidence

Authority NEVER derives from:
- Reviewer opinion
- AI reasoning
- Memory
- Assumptions
- Inference

## 5 Identity Purpose

Identity Cards establish:
- Canonical identity
- Stable identifiers
- Ownership
- Classification
- Authority
- Repository location
- Relationships
- Lifecycle
- Dependencies
- Consumers
- Providers
- Evidence references

Nothing beyond identity.

## 6 Required Identity Structure

Every Identity Card must contain the following mandatory fields:
- Identity ID
- Component Name
- Canonical Name
- Component Type
- Category
- Repository Path
- Owner
- Authority
- Lifecycle State
- Purpose
- Responsibilities
- Inputs
- Outputs
- Consumes
- Produces
- Dependencies
- Consumers
- Providers
- Repository Evidence
- Version
- Revision
- Identity Status
- Last Verified
- Notes

## 7 Identity Classifications

Identity Cards support the following component classifications:
- Documentation
- Governance Standard
- Template
- Repository Knowledge
- Architecture Knowledge
- Engineering Record
- Future Component
- Unknown Component

## 8 Identity Rules

The following rules govern component identity:
- Identity IDs are immutable.
- Canonical names never change without superseding.
- Repository location must reference physical evidence.
- Lifecycle must follow the README definitions.
- Identity never implies quality.
- Identity never implies implementation.
- Unknown remains Unknown.

## 9 Identity Relationships

Identity Cards define relationships only. They DO NOT evaluate them.
Examples of identity relationships:
- Parent
- Child
- Consumes
- Produces
- Depends On
- Used By
- Authority From
- Governed By

## 10 Repository Evidence

Every identity attribute must trace to Repository Evidence.
- No inferred identity.
- No estimated ownership.
- No guessed responsibilities.

## 11 Identity Findings

Identity findings are strictly descriptive.
- **Allowed:** Missing identity, Duplicate identity, Conflicting identity, Unknown identity.
- **Forbidden:** Bad architecture, Poor implementation, Needs redesign.

## 12 Identity Risks

Identity risks are repository-observable only.
- **Allowed:** Identity collision, Unknown ownership, Missing evidence, Duplicate identifiers.
- **Forbidden:** Performance risks, Security risks, Architecture risks.

## 13 Identity Readiness

Readiness ends ONLY at:
- Identity Ready
- Repository Identity Ready
- Component Identity Ready

It does NOT imply: Architecture Ready, Certification Ready, Merge Ready.

## 14 Verdict

Restrict verdict vocabulary ONLY to:
- Identity Established
- Identity Established with Limitations
- Identity Generation Failed

Explicitly state this verdict does NOT imply:
- Repository Review
- Architecture Verification
- Certification
- Repository Truth
- Merge
- Git
- Code Quality
- Architecture Quality
