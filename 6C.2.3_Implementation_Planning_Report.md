## 3. Investigation Reconciliation
The 6C.2.3 Investigation Report confirmed that the generated `Transcript` is intentionally dropped by the `WhisperExecutionMechanism` to preserve the status-only runtime contract. Because there is no persistence boundary inside the mechanism, the payload is genuinely lost during Runtime execution, causing downstream components to bypass the Runtime. The core challenge is injecting the domain persistence boundary (`ITranscriptRepository`) safely into the capability execution boundary (`WhisperExecutionMechanism`).

## 4. Confirmed Propagation Deficiency
The execution payload (`Transcript`) fails to reach its legitimate persistence owner when executed through the authorized Runtime path.

## 5. Payload Ownership Confirmation
* **Owner:** Capability Domain (Transcription).
* **Persistence Boundary:** `ITranscriptRepository`.
* **Payload Type:** `Transcript`.

## 6. Runtime Boundary Confirmation
The `ExecutionResult` and `AbstractExecutionMechanism` interfaces remain outcome-focused (`Tuple[ExecutionOutcome, Optional[str]]`). The Runtime Core remains completely ignorant of transcription types and repositories.

## 7. Existing Persistence Pattern Analysis
Background workers in ClipForge (`src/workers/app.py`) exhibit an established pattern for isolated database persistence: instantiating repositories with a fresh `AsyncSessionLocal()` scoped explicitly to the execution context. This pattern is ideal for mechanism-level persistence, as it avoids leaking global singleton sessions across threads or relying on FastAPI request scopes that aren't available to the Runtime Engine.

## 8. Candidate Propagation Analysis
* **Candidate A (Domain Service Persistence):** Modifying `WhisperTranscriptionService` to take a repository and persist the transcript. This violates the service's pure compute responsibility and risks shared singleton session leaks.
* **Candidate B (Mechanism-Level Domain Sink):** Injecting an `ITranscriptRepository` factory context into `WhisperExecutionMechanism`. This keeps the service pure, isolates the database transaction perfectly into the mechanism's execution thread, and preserves Runtime agnosticism entirely.

## 10. Selected Architecture
**Candidate B (Mechanism-Level Domain Sink)** is selected. The `WhisperExecutionMechanism` will receive a factory context-manager for `ITranscriptRepository`. It will bridge the transcription service call and the repository persistence call within the same `asyncio.run()` loop, cleanly preserving both the domain payload and the async transaction boundaries.

## 11. Exact Data Flow
1. `RuntimeInvocationFacade` executes `ExecutionEngine`.
2. `ExecutionEngine` delegates to `WhisperExecutionMechanism`.
3. `WhisperExecutionMechanism` spawns an isolated runner thread.
4. Thread executes `asyncio.run(transcribe_and_persist())`.
5. `ITranscriptionService.transcribe()` yields the exact `Transcript`.
6. Mechanism invokes the repository factory, yielding a clean `TranscriptRepository`.
7. `TranscriptRepository.save_transcript()` persists the exact `Transcript`.
8. Session closes cleanly.
9. Mechanism catches no exceptions and returns `ExecutionOutcome.SUCCESS`.
10. `ExecutionEngine` propagates the outcome payload-free.

## 12. DI Dependency Graph
* `RuntimeModule` provides an `@asynccontextmanager` factory function that uses `AsyncSessionLocal` to yield `TranscriptRepository`.
* `WhisperExecutionMechanism` receives this factory via constructor injection.
* `ExecutionMechanismRegistry` remains unaware of the repository.
* No circular dependencies or global state hacks are introduced.

## 13. Async / Transaction Analysis
`save_transcript` is `async` and uses SQLAlchemy sessions. The proposed `asynccontextmanager` explicitly limits the `AsyncSession` to the exact block containing `save_transcript`. Because the mechanism is already bridging into an async loop via `asyncio.run()`, we safely await the persistence within that same loop, keeping the transaction perfectly localized and preventing any leakage across threads.

## 14. Payload Identity Analysis
The `Transcript` object returned by `ITranscriptionService` is passed directly and immutably into `ITranscriptRepository.save_transcript()`. It is not deserialized, transformed, or reconstructed. Its identity and domain purity are guaranteed.

## 15. Success Path
If inference and persistence both complete without throwing exceptions, the mechanism correctly guarantees that the physical artifact exists in the domain sink, and subsequently returns `ExecutionOutcome.SUCCESS, None` to the Runtime.

## 16. Failure Boundary Analysis
If `save_transcript` raises an exception (e.g., `SQLAlchemyError`), it will propagate up inside the runner thread, caught by the mechanism's generic `except Exception` block. It translates to `ExecutionOutcome.FAILED` with a generic string. This prevents silent execution successes upon persistence failure. Detailed retry and classification logic is explicitly deferred to 6C.2.4.

## 17. Idempotency Analysis
`TranscriptRepository.save_transcript()` is already implemented to query for an existing transcript by `video_asset_id` and cleanly `delete()` it before insertion. Therefore, repeated persistence of the same asset is intrinsically idempotent and safe.

## 26. Risk Analysis
* **Risk:** The mechanism thread panics during persistence.
* **Mitigation:** The exception is safely caught by the `nonlocal` capture and correctly fails the execution intent, preventing a false positive.
* **Risk:** The `AsyncSessionLocal` leaks a connection.
* **Mitigation:** The strict `@asynccontextmanager` wrapper guarantees `__aexit__` is called, closing the session even on exceptions.
