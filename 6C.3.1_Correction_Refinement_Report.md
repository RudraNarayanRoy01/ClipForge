## 3. Previous Blocker Summary
The previous implementation planning phase identified four critical blockers:
1. **Target Ownership Blocker:** `RuntimeInvocationFacade` requires the caller to provide `available_targets`, forcing the Application to adopt provider-awareness.
2. **Transient Result Blocker:** Application orchestration workflows (e.g., `detect_topics`) generate intermediate transient results. `ExecutionResult` intentionally forbids payloads, severing the return path.
3. **Payload Propagation Blocker:** Because transient results lack domain repositories, 6C.2.3's mechanism-level persistence pattern cannot save them.
4. **Transaction Blocker:** Moving multi-step orchestrations (e.g., `generate_clips`) into the Runtime Execution Mechanism strips them of Application context (like `project_id`) required for atomic persistence.

## 4. Target Ownership Investigation
**Current Ownership Chain:**
- Discover candidates: Undefined / Caller-provided
- Filter candidates: `TargetSelector`
- Select target: `TargetSelector`
- Provider/Model selection: `RuntimePipeline` (via policy and routing)

The requirement for the Application to provide `available_targets` to the `RuntimeInvocationFacade` is a **contractual leak**. The Runtime ecosystem already possesses the `ProviderRegistry` (in `src.runtime.core.provider_registry.py`), which owns the authoritative list of available providers.

## 5. Target Discovery Alternatives
**Evaluated Options:**
- **Option A:** `invoke(intent, context)` with Runtime-owned target discovery.
- **Option B:** `invoke(request)` (requires Runtime to construct context).
- **Option C:** `invoke(intent, context, target_source)` (Runtime-owned infrastructure).
- **Option D:** Expose Runtime-owned candidate provider.

**Selected Alternative:** **Option A**. 
The `RuntimeInvocationFacade` contract should be refined to `invoke(intent, context)`. The Facade will internally discover `available_targets` by querying the `RuntimeProviderRegistry` and mapping `ProviderInfo` to `TargetDescription`. This perfectly isolates target discovery within the Runtime Core and shields the Application completely.

## 6. Transient Result Investigation
A complete trace of `detect_topics` reveals:
`GenerateClipsUseCase` → `ILLMReasoningEngine.detect_topics` → `AIProviderLLMEngineAdapter` → `IAIProvider` → `TopicSegment` → `GenerateClipsUseCase` constructs `TimelineContext`.

`TopicSegment` is explicitly an **intermediate application orchestration value**. It is not a persistent domain entity. It is consumed immediately in the same transaction to construct the next domain input. The Runtime is correctly agnostic to it.

## 7. Payload Ownership Analysis
- **Persistent Domain Payload:** e.g., `Transcript`. Can be saved by the Mechanism (6C.2.3 pattern).
- **Intermediate Application Value:** e.g., `List[TopicSegment]`. Must be returned synchronously to the orchestrator.
- **Runtime Metadata:** e.g., Execution timing, target info. Owned by `ExecutionResult`.
- **Provider-Native Result:** e.g., Raw JSON. Adapted by Infrastructure.

## 8. Transaction Analysis
In `GenerateClipsUseCase.execute()`, the orchestration controls a unified transaction context. For example, `generate_clips` ranks candidate clips, and the Application attaches the `project_id` before persistence. Attempting to force this orchestration into a Runtime Mechanism violates transaction boundaries because the Mechanism executes generically, devoid of `project_id` state.

**Conclusion:** The Application must retain orchestration and transaction ownership. The Runtime must only be used as a boundary for **provider execution**, not for encapsulating domain orchestrations.

## 10. Selected Correction
**Target Architecture (Capability Context Pattern):**
```text
Application Orchestration (GenerateClipsUseCase)
    ↓ (Calls domain port, preserving transaction context)
Domain Port (ILLMReasoningEngine)
    ↓
Infrastructure Runtime Adapter (RuntimeReasoningAdapter)
    ↓ (Constructs CapabilityContext & ExecutionIntent)
RuntimeInvocationFacade (Option A contract)
    ↓ (Internally discovers targets via ProviderRegistry)
ExecutionEngine
    ↓
Capability Execution Mechanism (LLMExecutionMechanism)
    ↓ (Mutates CapabilityContext to attach domain result)
Provider Adapter (AIProviderLLMEngineAdapter)
```
After `invoke()` returns a successful `ExecutionResult`, the `RuntimeReasoningAdapter` retrieves the transient payload from the `CapabilityContext` (passed via the `ExecutionIntent.payload`) and returns it natively to the Application. 

**Architectural Wins:**
1. `ExecutionResult` remains 100% pure (no generic payloads).
2. Application layer code is **untouched**. It remains completely agnostic to Runtime.
3. Transactions and orchestration remain in the Application.
4. Target ownership correctly shifts downward into the Runtime.

## 13. 6C.2.1–6C.2.4 Preservation Audit
- **6C.2.1:** `ExecutionResult` and `ExecutionOutcome` semantics remain unmodified.
- **6C.2.2:** Payload ownership is preserved. The Runtime does not adopt `payload: Any` on the output. `ExecutionIntent.payload` safely ferries the input envelope, conforming to its existing definition.
- **6C.2.3:** Capability-specific payloads remain domain-owned. Transcription maintains its domain sink; transient results utilize capability contexts. 6C.2.3 is explicitly capability-specific and not wrongly generalized to transients.
- **6C.2.4:** Failure semantics (`REJECTED`, `FAILED`, `SUCCESS`) remain authoritative and unchanged.
