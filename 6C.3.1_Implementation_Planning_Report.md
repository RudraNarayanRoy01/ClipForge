## 3. Previous Investigation Reconciliation
The initial planning phase correctly identified architectural blockers: Runtime leaked target discovery (via `available_targets`), and `ExecutionResult` correctly rejected payloads, trapping transient capability results. The Correction & Refinement phase successfully resolved these by moving target discovery downward and utilizing CapabilityContexts. This implementation plan directly executes that corrected design.

## 4. Corrected Architecture
**Execution Path Design:**
```text
Application Workflow (e.g., GenerateClipsUseCase)
    ↓
Infrastructure Runtime Adapter (e.g., RuntimeReasoningAdapter)
    ↓  (Creates CapabilityContext & ExecutionIntent)
RuntimeInvocationFacade 
    ↓  (Discovers Targets via RuntimeProviderRegistry)
ExecutionEngine
    ↓
Capability Execution Mechanism (e.g., LLMExecutionMechanism)
    ↓  (Executes via Provider, Mutates CapabilityContext)
Provider Adapter (e.g., IAIProvider)
```
The adapter extracts the domain result from the `CapabilityContext` after the `ExecutionResult` (outcome only) is returned synchronously.

## 6. Runtime Boundary Analysis
The `RuntimeInvocationFacade` is correctly positioned as the universal admission gate. No Application orchestration code will bypass it for execution.

## 7. Target Discovery Ownership
**Decision A Validation:** Target discovery shifts entirely to the Runtime. The Application and Infrastructure Adapters will **never** construct or provide `TargetDescription`s.

## 8. ProviderRegistry Analysis
`RuntimeProviderRegistry` (in `backend/src/runtime/core/providers.py`) correctly owns `ProviderRegistration` and `ProviderDescriptor`. It is authoritative, injectable, and contains no execution state, making it the perfect internal source for `RuntimeInvocationFacade`.

## 9. TargetDescription Mapping
`RuntimeInvocationFacade` will internally map:
`ProviderRegistration.descriptor.identity.identifier` → `TargetDescription.target_id` and `provider`.
`ProviderRegistration.descriptor.category.value` → `TargetDescription.target_class`.

## 10. RuntimeInvocationFacade Plan
- **Constructor:** Inject `provider_registry: RuntimeProviderRegistry`.
- **Invoke Signature:** `def invoke(self, intent: ExecutionIntent, planning_context: PlanningContext) -> ExecutionResult`
- **Behavior:** Constructs `available_targets` internally and passes them to `RuntimePipeline.process()`.

## 11. CapabilityContext Analysis
**Decision C Validation:** 
- **Owner:** Infrastructure Adapter.
- **Lifetime:** Ephemeral (Garbage collected after adapter returns).
- **Mutator:** Capability Execution Mechanism.
- **Type Safety:** Strongly typed per capability (e.g., `LLMCapabilityContext` holds `AIResponse`, not `Any`).
- **Semantic Integrity:** Prevents generic payload proliferation into Runtime core.

## 12. Transient Result Ownership
Transient results (like `List[TopicSegment]`) remain intermediate Application values. They are populated into the CapabilityContext by the Mechanism and immediately read by the Adapter. No domain repository is forced upon transient workflows.

## 13. RuntimeReasoningAdapter Plan
Implements `ILLMReasoningEngine`. Handles prompt construction and schema definition. Wraps `AIRequest` in `LLMCapabilityContext`, invokes the Facade, and maps the resulting `AIResponse` into Domain `TopicSegment`/`ClipSegment` lists.

## 14. RuntimeTranscriptionAdapter Plan
Implements `ITranscriptionService`. Wraps `TranscriptionRequest` in `TranscriptionCapabilityContext`, invokes the Facade. Retrieves the `Transcript` directly from the Context to return to the caller immediately.

## 15. LLMExecutionMechanism Plan
Implements `AbstractExecutionMechanism[LLMExecutionWorkload]`. Receives `IAIProvider` in its constructor. Executes `provider.generate(request)` and attaches the result directly to `LLMCapabilityContext.response`. Returns `ExecutionOutcome.SUCCESS` or `FAILED`.

## 16. Application Transaction Preservation
**Decision D Validation:** `GenerateClipsUseCase` retains complete ownership of its multi-step orchestration, persistence sequencing, and `project_id` state. The Runtime executes individual stateless LLM operations.

## 25. Per-File Change Intent
1. **`runtime_invocation_facade.py`**: Inject `RuntimeProviderRegistry`, remove `available_targets` from `invoke()`, dynamically map `ProviderRegistration` to `TargetDescription`. Eliminates Application hardware/provider awareness.
2. **`runtime_reasoning_adapter.py`**: Creates capability context, abstracts away prompt structure, dispatches via Facade, synchronously translates context result into Domain objects.
3. **`runtime_transcription_adapter.py`**: Creates transcription capability context, dispatches via Facade, synchronously returns transcript.
4. **`llm_execution_mechanism.py`**: Executes raw LLM workloads, catching exceptions and returning strict `ExecutionOutcome` while populating context.
5. **`transcription/execution/workload.py`**: Introduce `TranscriptionCapabilityContext`.
6. **`transcription/execution/mechanism.py`**: Update `execute()` to assign `transcript` to the `CapabilityContext`.

## 28. Dependency/DI Impact
Creating `RuntimeReasoningAdapter` requires injecting `RuntimeInvocationFacade`. This establishes the Application dependency on Runtime Core, which will be finalized in 6C.3.2.

## 29. Security Review
Safe. Execution contexts are short-lived and garbage-collected per invocation, preventing cross-request pollution.

## 30. Risk Analysis
- **Target Selection Collision:** High-level abstractions protect the RuntimePipeline from target absence.
- **Payload Loss:** Eliminated via CapabilityContext.
- **Memory Leaks:** `CapabilityContext` drops out of scope immediately after adapter execution.

## 31. Stop-Condition Audit
None triggered. `ExecutionResult` remains pure. CapabilityContext is strongly typed. Application retains orchestration.
