## 5. Authoritative Runtime Boundary Identification
- **What should Application call?** According to `backend/src/runtime/README.md`, `ExecutionEngine` is the canonical authoritative Runtime Execution orchestrator. The `RuntimeInvocationFacade` is also provided to wrap admission and execution boundaries.
- **What does Application actually call?** The Application calls legacy domain capability ports (e.g., `ILLMReasoningEngine`, `ITranscriptionService`, `ICampaignIntelligence`) directly. It does NOT call `ExecutionEngine` or `RuntimeInvocationFacade`.

## 6. Application → Runtime Dependency Graph
- **Findings:** The Application layer contains **zero** imports from `src.runtime`. 
- **Analysis:** Rather than properly importing and depending on the authoritative `RuntimeInvocationFacade` or `ExecutionEngine`, the Application relies on legacy interfaces that bypass the Runtime completely.

## 7. Direct Runtime-Internal Access Audit
- **Findings:** No direct access to Runtime internals (e.g., `ExecutionTarget`, `ExecutionAdmission`) was found in the Application layer. The bypass occurs by avoiding the Runtime entirely, rather than tangling with its internals.

## 8. Manual Runtime Construction Audit
- **Findings:** The Application layer does not manually construct Runtime infrastructure. Bootstrapping is cleanly isolated in `runtime_module.py`.

## 9. Direct Provider Invocation Audit
- **Findings:** The Application layer invokes provider adapters directly via injected legacy domain ports.
- **Evidence:** 
  - `AIProviderLLMEngineAdapter` adapts `IAIProvider` and is bound directly to `ILLMReasoningEngine`.
  - `CampaignIntelligenceService` injects `IAIService` (resolved to `DefaultAIService`) which directly calls the `ProviderFactory`.
  - `WhisperTranscriptionService` is bound directly to `ITranscriptionService`.
- **Classification:** **Strong Bypass**. The Application layer invokes provider implementations (via domain ports) without routing through the authoritative `ExecutionEngine`.

## 10. Execution Decision Leakage Audit
- **Findings:** Execution decisions (such as provider selection, routing, fallback, and retry strategies) that should be owned by the Runtime are absent in the Application layer's execution path because the Runtime is bypassed. The legacy provider adapters execute single-shot calls directly (e.g., `asyncio.run(self._provider.generate(...))`), leaking the decision of "how to execute" to the concrete adapters rather than the Runtime engine.

## 11. Result Consumption Audit
- **Findings:** The Application layer consumes pure Domain representations (`Transcript`, `ClipSegment`, etc.) directly from the legacy ports. It does not receive `ExecutionResult` or `ExecutionOutcome` semantics because it bypasses the Runtime.
- **Violation:** The architecture requires execution results to be wrapped in the `ExecutionResult` standard from the Runtime core, which the Application fails to consume.

## 14. Clean Architecture Dependency Audit
- **Desired:** Application → Runtime Abstraction → Runtime Implementation → Infrastructure
- **Actual:** Application → Domain Port → Infrastructure Adapter → Provider SDK
- **Violation:** The canonical `src.runtime` module is isolated and ignored by the Application.

## 15. Bootstrap / Application Boundary Audit
- **Findings:** `runtime_module.py` properly registers `ExecutionEngine` and `RuntimeInvocationFacade`. However, `intelligence_module.py` and `infrastructure_module.py` bind domain ports (e.g. `ILLMReasoningEngine`, `ITranscriptionService`) directly to infrastructure adapters. 
- **Conclusion:** The Bootstrap properly isolates construction, but the DI bindings wire the Application directly to the providers, structurally bypassing the Runtime.

## 16. Production DI Observations
- **Observation:** The `ExecutionEngine` is available in the DI container, but it is not injected into the Application services. The Application services ask for legacy domain ports instead.
- **Note:** Broad DI restructuring belongs to 6C.3.2. We will not redesign the container here, but we acknowledge the DI bindings facilitate the bypass.

## 17. Architecture Test Audit
- **Findings:** Tests in `backend/tests/architecture` enforce that `Runtime` modules do not import `Application` or `Domain` modules (e.g., `test_application_neutrality`).
- **Gap:** There are no architecture tests enforcing that `Application` execution must enter through the authoritative `RuntimeInvocationFacade` or `ExecutionEngine`. Existing tests permit the Application bypasses.

## 18. Test / Production Divergence
- **Findings:** The Application bypasses the Runtime in production, rendering any Runtime reliability guarantees (e.g., retry, failover) inactive for critical pipelines.
