# 6C.4.1 Correction Refinement Report

## 1. Batch Identity
- **Milestone:** 6C — Runtime Stabilization, Reconciliation, Hardening & Completion
- **Sprint:** 6C.4 — Execution Reliability, Environment & Security
- **Batch:** 6C.4.1 — Concrete Execution Path Reliability Correction

## 2. Baseline
- **Commit:** 93cf2169f25bc02bbb5c181e5cdf7aa0163cce06
- **Architecture:** Synchronous Runtime bridging to Asynchronous Providers via `asyncio.run()`.

## 3. Confirmed Deficiencies
- **R-001:** Cross-loop Async Resource Corruption (`httpx.AsyncClient` and `asyncio.Lock` break across Execution Engine invocations).
- **R-002:** Unenforced Transcription Timeout (`WhisperExecutionMechanism` blocks indefinitely on thread join).
- **R-003:** Uncancelable Background Tasks (Blocking synchronous boundaries prevent cancellation propagation).

## 4. Architectural Conflict
The `ExecutionEngine` operates synchronously, isolating the Application boundary from provider execution logic. However, the providers (`IAIProvider`, `ITranscriptionService`) are asynchronous. The current mechanisms attempt to bridge this using `asyncio.run()`, which creates a transient event loop for each request. This structurally conflicts with 6C.3.2 Production Composition, which instantiates async provider resources (like sockets and locks) on the global startup event loop.

## 5. Root Cause
Mixing DI-injected, singleton asynchronous resources (bound to the application startup loop) with transient execution loops (created per-execution) results in `RuntimeError: Event loop is closed` and cross-loop state corruption.

## 6. Event Loop Ownership Analysis
- **Current Owner:** Transient loop created per-execution by the Mechanism.
- **Resource Owner:** Global startup loop (via DI).
- **Conflict:** Resources must be owned by the loop that executes them.

## 7. Provider Resource Lifecycle Analysis
- `OllamaProvider`: Injects `httpx.AsyncClient` globally. Must be scoped to the execution loop.
- `WhisperTranscriptionService`: Injects `asyncio.Lock` globally. Must be independent of event loops to support cross-loop thread safety.

## 8. Option A Analysis (Full Async Runtime)
- Changes `ExecutionEngine` and `RuntimeInvocationFacade` to async.
- Violates Stop Condition 1 (Redesigning Runtime Core) and 5 (Redesigning 6C.3.1 Application boundaries).
- **Verdict:** REJECTED.

## 9. Option B Analysis (Sync→Async Runtime Bridge)
- Requires a persistent background Runtime event loop. 
- Introduces massive lifecycle complexity to manage worker threads, shutdown signals, and cross-thread future synchronization.
- **Verdict:** REJECTED (Excessive complexity for 6C.4.1).

## 10. Option C Analysis (Sync Providers)
- Changes `IAIProvider` and `ITranscriptionService` to synchronous interfaces (`def generate`).
- Radically simplifies execution, but forces changes to Domain Ports and potentially Application Use Cases that currently `await` these interfaces.
- **Verdict:** REJECTED (Unnecessary Application impact when bounded provider fixes exist).

## 11. Option D Analysis (Lazy Async Resources)
- Retains `asyncio.run()` in Mechanisms (Transient Event Loops).
- Shifts resource creation from DI-startup into the provider's execution method (`_do_generate`).
- Uses `threading.Lock` for cross-loop singleton protection.
- Preserves all Domain Ports and Runtime Core exactly as they are.
- **Verdict:** ACCEPTED.

## 12. Option E Analysis (Dedicated Worker)
- Requires creating a new Runtime Subsystem to manage a long-lived worker thread.
- **Verdict:** REJECTED (Violates Stop Condition regarding new subsystems).

## 14. Timeout Architecture (R-002)
- **Owner:** Execution Mechanism.
- **LLM:** Enforced by passing `target.timeout_seconds` to the lazily instantiated `httpx.AsyncClient`.
- **Whisper:** Enforced by using `t.join(timeout=target.timeout_seconds)` in the mechanism. Returns `ExecutionOutcome.FAILED` if exceeded.

## 15. Cancellation Architecture (R-003)
- **Owner:** Execution Mechanism.
- **LLM:** Soft-cancellation achieved organically. If timeout triggers, the transient loop tears down, safely severing the socket.
- **Whisper:** **DEFERRED.** Native C++ `faster-whisper` lacks cancellation tokens. The thread is orphaned upon timeout and will gracefully terminate in the background upon completion. A full process-isolation cancellation architecture is deferred to future work.

## 16. Retry Boundary
- **DEFERRED.** The investigation confirmed that basic execution reliability can be achieved without retries. Retry orchestration (via `RuntimeRetryManager`) is out of scope for 6C.4.1 and deferred to a dedicated orchestration batch.

## 17. Shutdown Architecture
Because transient event loops are used (`asyncio.run()`), they shut down cleanly and deterministically at the end of every execution block. The Runtime requires no global shutdown hooks for execution pathways.

## 18. DI Lifecycle Reconciliation
`OllamaProvider` remains a singleton. However, `httpx.AsyncClient` is removed from its constructor. The DI composition is updated to stop injecting the HTTP client. The provider manages its own transient socket lifecycle per-request.

## 19. Application Impact
**ZERO.** No Domain Ports, Use Cases, or Adapters are changed.

## 20. Runtime Impact
**MINIMAL.** `ExecutionEngine`, `RuntimeExecutionBoundary`, and `RuntimeInvocationFacade` are completely untouched. Only `LLMExecutionMechanism` and `WhisperExecutionMechanism` receive minor timeout logic adjustments.

## 21. Capability Context Preservation
Preserved. Execution results remain attached to `LLMCapabilityContext` and `TranscriptionCapabilityContext`.

## 22. ExecutionResult Preservation
Preserved. `ExecutionResult` remains completely payload-agnostic.

## 23. 6C.2.x Preservation
PASS. Outcomes remain truthful (R-002 timeout yields FAILED, not SUCCESS).

## 24. 6C.3.x Preservation
PASS. Application boundaries and configuration flow are untouched.

## 25. 6C.4.2 Boundary
Preserved. The native crash observed during investigation will no longer occur because cross-loop corruption is fixed; any future CUDA/dependency faults will truthfully bubble up as FAILED outcomes.

## 26. 6C.4.3 Boundary
Preserved. No test isolation or environment modifications required.

## 27. Stop-Condition Evaluation
No stop conditions are triggered by Option D. The architecture remains entirely within the bounds of the Provider and Mechanism layers.

## 28. Recommended Architecture
**Option D: Lazy Async Resource Ownership + Transient Event Loops**

## 29. Exact Rationale
This is the only architecture that mathematically resolves the cross-loop event loop crashes without modifying synchronous Domain Ports, rewriting Runtime Core, or introducing complex global worker threads. It acknowledges the synchronous nature of the current Runtime and safely maps it to asynchronous providers by strictly isolating resource scopes.
