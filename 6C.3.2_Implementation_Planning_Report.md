## 4. Container Architecture
Implemented in `backend/src/infrastructure/di/container.py`.
- **Instantiation:** Constructed synchronously.
- **Registration:** Modules register abstractions mapping to implementations or factories.
- **Resolution:** Constructor dependencies are resolved automatically via `inspect.signature` and type hints.
- **Factories:** Can be evaluated lazily or eagerly depending on when `resolve()` is called. 
- **Overwrites:** Successive registrations for the same interface overwrite previous bindings.
- **Behavior:** It behaves deterministically. Circular dependencies are detected by maintaining a resolution stack.

## 7. RuntimeProviderRegistry Analysis
- **Constructor Dependencies:** None.
- **Registration API:** `register_provider(descriptor: ProviderDescriptor)`
- **Discovery API:** `enumerate_providers()`, `get_provider(identity)`
- **Representation:** Utilizes purely architectural identifiers via `ProviderDescriptor`, `ProviderIdentity`, and `ProviderCategory`.
- **Lifecycle:** Singleton.
- **Role:** Central catalog consumed by `RuntimeInvocationFacade` to populate `available_targets`.
- **Adaptation:** Existing providers do not need modification. We simply map them to corresponding `ProviderDescriptor` registrations during `RuntimeModule` bootstrap.

## 8. Mechanism Registry Analysis
- **Registration:** Mechanisms are manually instantiated and registered into `ExecutionMechanismRegistry` using `registry.register(...)`.
- **Discovery:** Looked up via `get_mechanism()` during `ExecutionEngine` execution.
- **Whisper:** Registered cleanly.
- **LLM:** Not registered. `LLMExecutionMechanism` expects an `IAIProvider`. This can be securely provided via `container.resolve(IAIProvider)` inside `RuntimeModule.register` without creating any circular dependencies.

## 9. LLM Composition Analysis
- **Current state:** `IAIProvider` is built in `IntelligenceModule` and injected directly into `AIProviderLLMEngineAdapter`.
- **Desired state:** `IAIProvider` remains built by `IntelligenceModule`. `IntelligenceModule` binds `ILLMReasoningEngine` to `RuntimeReasoningAdapter`. `RuntimeModule` resolves `IAIProvider` and injects it into a new `LLMExecutionMechanism` instance, which is then registered in the `ExecutionMechanismRegistry` along with an anonymous or inline `LLMNormalizer` fulfilling the `WorkloadNormalizer` protocol for `LLMExecutionWorkload`.

## 10. Transcription Composition Analysis
- **Current state:** `WhisperTranscriptionService` is registered globally as `ITranscriptionService`.
- **Desired state:** We must separate the physical provider from the domain port. Register the concrete `WhisperTranscriptionService` via a factory, and bind `ITranscriptionService` to `RuntimeTranscriptionAdapter`. `RuntimeModule` then resolves `WhisperTranscriptionService` to construct the `WhisperExecutionMechanism`. This preserves the 6C.2.3 payload path correctly without circular dependencies.

## 13. Circular Dependency Analysis
The corrected graph was verified for circular dependencies:
1. `ILLMReasoningEngine` (`RuntimeReasoningAdapter`) -> `RuntimeInvocationFacade` -> `ExecutionEngine` -> `ExecutionMechanismRegistry` -> `LLMExecutionMechanism` -> `IAIProvider` (OllamaProvider). -> **NO CYCLE**
2. `ITranscriptionService` (`RuntimeTranscriptionAdapter`) -> `RuntimeInvocationFacade` -> `ExecutionEngine` -> `ExecutionMechanismRegistry` -> `WhisperExecutionMechanism` -> `WhisperTranscriptionService`. -> **NO CYCLE**

The potential cycle in transcription is avoided by registering `WhisperTranscriptionService` to its concrete class instead of the domain port in `InfrastructureModule`.
